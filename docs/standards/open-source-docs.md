# 公开开源项目文档规范

本规范管理公开仓库的文档体系、项目类型研究、README 语言决策、信息架构和发布门禁。GitHub Markdown 的行文与排版细则见 [github-content-writing.md](github-content-writing.md)；本机与私有项目文档见 [local-dev-docs.md](local-dev-docs.md)。

## 目标与适用范围

适用于公开 GitHub/GitLab/Gitee 项目的 README、安装指南、使用文档、架构说明、贡献指南、发布说明、示例和项目站点。

目标是帮助目标用户快速判断项目价值、理解适用范围、成功安装并完成第一个任务；同时为维护者提供准确、可持续维护的技术记录。

## 1. 先研究项目，再设计文档

撰写前先识别项目类型、主要用户、交付形态和成熟度。研究同类型高质量开源项目的文档组织方式，不能只套一个通用 README 模板。

按项目类型选择代表性样本：

| 项目类型 | 优先研究的文档 | 需要提炼的内容 |
| --- | --- | --- |
| CLI / 开发工具 | 安装、命令参考、配置、退出码、示例 | 快速上手、命令分组、Shell 示例、平台兼容 |
| SDK / Library | Quick Start、API、类型、版本兼容 | 最小调用、核心 API、错误处理、版本策略 |
| Web / 自托管服务 | 部署、环境变量、Compose、升级、备份 | 部署路径、依赖、数据持久化、健康检查 |
| Agent / AI 基础设施 | 概念、工具接入、配置、权限、安全、工作流 | Agent 交互边界、工具能力、模型配置、权限和数据流 |
| 算法 / 研究项目 | 论文、方法、数据、实验、复现、局限 | 问题定义、公式、基线、数据集、随机种子和复现步骤 |

研究应回答：目标用户是谁、项目解决什么问题、最短成功路径是什么、有哪些关键约束、文档如何分层、哪些内容适合放在 README，哪些应放到独立页面。

优先检查上游源码、官方文档、配置样例和可执行测试。高星项目只作为信息架构与表达方式的参考，不能作为本项目功能或性能的证据。

## 2. 确定文档范围和信息架构

先从真实功能、用户任务和维护需求列出文档清单，再决定哪些内容需要独立文件。常见结构如下：

| 文档 | 主要读者 | 主要任务 |
| --- | --- | --- |
| README | 首次访问者 | 判断项目价值，找到安装和使用入口 |
| Quick Start | 新用户 | 在最短路径完成一次成功操作 |
| Installation | 用户 / 运维 | 按平台和部署方式安装 |
| Usage / Guides | 日常用户 | 完成具体任务 |
| Configuration | 使用者 / 管理员 | 理解配置、默认值和安全边界 |
| Architecture / Design | 维护者 / 贡献者 | 理解模块、数据流和设计决策 |
| API / CLI Reference | 集成开发者 | 查询完整参数、接口和返回值 |
| Troubleshooting | 用户 / 运维 | 根据现象定位和解决问题 |
| Contributing | 贡献者 | 了解开发、测试和提交规范 |
| Security | 用户 / 维护者 | 报告漏洞并理解安全政策 |
| Changelog / Releases | 用户 / 维护者 | 查看版本变化、兼容性和升级信息 |
| License / NOTICE | 所有读者 | 确认许可和第三方通知 |

只创建确实有内容的文档。小型项目不需要为了表格齐全而创建空章节；大型项目应把安装、配置、API 和运维细节从 README 分离。

每个主题只有一个权威来源。README 负责导览和摘要，详细页负责完整说明，交叉引用而不是复制整段内容。

## 3. 决定主文档语言与 i18n 策略

主语言应根据目标用户、项目生态和维护能力决定，而不是默认所有仓库都使用中文或英文。

| 项目主要受众 | 推荐主语言 | 补充策略 |
| --- | --- | --- |
| 全球开发者 / 国际开源生态 | 英文 | 提供中文 README 或完整中文文档 |
| 中国用户为主，且项目面向国内场景 | 简体中文 | 为国际集成者提供英文简介、安装入口和关键术语 |
| 中英文用户均为核心受众 | 英文或中文择一作为规范版本 | 提供另一语言的同步版本与语言切换链接 |
| 内部 / 本地项目 | 团队实际工作语言 | 不为公开传播而额外维护翻译 |

决策时检查 Issues/PR 使用语言、用户分布、生态默认语言、平台与依赖文档语言、搜索关键词、维护者翻译能力，以及项目未来用户群。

### i18n 文档规则

- 在 README 开头提供语言切换链接，例如 `[简体中文](README.zh-CN.md) | [English](README.md)`。
- 明确哪份文档是规范版本，其他语言版本应同步更新。
- 翻译技术术语时保留原始产品名、命令、参数、路径、环境变量和 API 名称。
- 不要只翻译标题而遗漏安装、配置、安全和兼容性说明。
- 不确定的翻译标记待确认，不编造本地化产品功能。
- 更新主文档时，检查其他语言版本是否出现失效链接或过期步骤。

避免维护多个内容完全相同、却没有语言或版本差异的 README 副本。

## 4. README 的内容组织

README 的第一屏必须让读者理解项目是什么、解决什么问题，以及下一步在哪里。

按项目实际情况组织，推荐次序：

1. 项目名称与一句话定位。
2. 关键价值、核心能力和适用对象。
3. 真实的预览、架构图、演示或关键输出（有价值时）。
4. 最短安装路径和 Quick Start。
5. 常用功能、使用场景和关键配置入口。
6. 架构、平台兼容、限制和安全边界（只展示读者决策所需内容）。
7. 完整文档、贡献、版本和许可证入口。

README 是项目入口，不是把所有内部设计、历史过程和配置细节堆在一起的总档案。长篇内容移入独立文档，并在 README 中提供准确链接。

### 发布会原则

将公开 README 写成一份以用户价值为主线的产品介绍：先呈现项目解决的问题、关键能力和使用收益，再说明实现方式与使用路径。让读者先理解为什么值得使用，再了解如何使用。

执行以下要求：

- 以真实能力和用户场景组织叙述，不按开发时间线罗列工作过程。
- 用具体功能、输入输出、示例和可验证事实支撑价值主张。
- 重点展示项目已经具备的优势、差异化能力和设计选择。
- 将性能、兼容性、覆盖范围等数据放入明确条件和测试环境中说明。
- 对不成熟能力、限制和未验证事项如实披露，放在适当的边界或限制章节。
- 不使用自我贬低式或自我否定式措辞，例如“遗憾的是”“仅仅”“仍明显落后”“效果有限”等；改为描述当前支持范围、适用条件和实际行为。
- 对表现较弱的数据提供必要上下文和改进方向，但不能删减关键数字、改换口径或夸大结论。
- 不写无法从代码、测试、官方资料或实际产品中验证的宣传性承诺。

发布会原则用于调整叙述顺序和重点，不允许改变事实、隐藏对使用有实质影响的限制或制造虚假比较。

## 5. 文档内容必须来自可验证事实

以仓库实际内容为准，检查：

- 源码、目录、清单文件和默认配置。
- 真实安装器、命令、参数、环境变量和平台要求。
- 测试、CI、示例输出和可复现操作。
- 上游依赖及其官方文档。
- 现有 Issue、PR 和明确记录的设计决策。

每项重要说明都应区分：

- **已验证：** 已执行、可复现，或由权威源代码/官方文档直接确认。
- **有依据但未执行：** 步骤来源明确，但当前环境尚未实际验证。
- **待确认：** 依赖版本、地区、账号灰度或缺少来源，不能给出确定承诺。

不得编造命令、文件、功能、性能数据、市场上架状态、兼容版本和测试结果。平台界面可能变化时，注明版本或地区边界并链接官方资料。

## 6. 示例和可复现性

示例优先使用最小、完整、可以复制运行的路径。每个示例都要说明前置条件、输入、执行命令和预期结果。

- 配置示例使用真实键名和合法值。
- 敏感凭据使用占位符，并说明如何安全配置。
- 示例数据应明确标注为示例，不伪装成生产数据。
- 算法和研究项目说明数据集、预处理、参数、随机种子、硬件和评价指标。
- 发布性能数字时提供测试脚本或方法、环境和版本。
- 代码改动后同步更新示例和文档。

## 7. 许可证、来源和国际化发布

发布前按照 [第三方内容与许可证审查规范](third-party-license-review.md) 检查文件级许可证、来源、署名、NOTICE 和分发义务。

确保：

- 项目许可证与实际文件来源和授权边界一致。
- 第三方文件保留其版权、许可证和必要通知。
- README 的许可证声明指向仓库真实存在的许可证文件。
- 语言版本的许可证和贡献政策保持一致。
- 图片、字体、数据集、模型和二进制资产具有明确来源与许可。

## 8. 公开文档发布门禁

文档发布前完成以下检查：

- [ ] 已识别项目类型、主要用户和文档维护者。
- [ ] 已研究同类高质量项目的文档结构，并记录采用或不采用的设计。
- [ ] 已决定 README 主语言和 i18n 方案。
- [ ] README 的第一屏清楚说明项目价值和最短使用路径。
- [ ] 功能、命令、路径、配置、版本和数据均来自真实证据。
- [ ] 安装步骤在目标平台上实际执行，或明确标记尚未执行。
- [ ] 所有相对链接、外部链接、图片和代码引用有效。
- [ ] 示例与当前版本一致，能够复现预期结果。
- [ ] 许可证、版权、NOTICE 和第三方来源通过检查。
- [ ] GitHub 页面最终渲染正常，移动端宽表格和长代码有合理处理。
- [ ] 已完成对照源码的事实审查和独立文档审查。
- [ ] 发布信息没有把计划、假设或未验证能力写成现状。
