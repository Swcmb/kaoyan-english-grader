# 公开开源项目文档规范

本规范负责公开仓库的文档范围、项目类型研究、信息架构、README 语言与 i18n、发布内容和验收。GitHub Markdown 排版见 [github-content-writing.md](github-content-writing.md)；本机和私有文档见 [local-dev-docs.md](local-dev-docs.md)。

## 目标与适用范围

适用于公开 GitHub、GitLab、Gitee 项目的 README、安装指南、使用文档、架构说明、贡献指南、发布说明、示例和项目站点。文档应帮助用户判断项目价值、理解边界、完成安装并执行第一个任务，同时为维护者提供准确且可持续维护的技术记录。

## 1. 先研究项目，再设计文档

撰写前确认项目类型、主要用户、交付形态和成熟度。研究同类型高质量项目的文档组织方式，提炼适用做法，不直接套用通用模板。

| 项目类型 | 优先研究 | 提炼内容 |
| --- | --- | --- |
| CLI / 开发工具 | 安装、命令、配置、退出码和示例 | Quick Start、命令分组、Shell 与平台兼容 |
| SDK / Library | Quick Start、API、类型和版本兼容 | 最小调用、核心 API、错误处理和版本策略 |
| Web / 自托管服务 | 部署、环境变量、Compose、升级和备份 | 部署路径、依赖、数据持久化和健康检查 |
| Agent / AI 基础设施 | 概念、工具接入、权限、安全和工作流 | Agent 边界、工具能力、模型配置和数据流 |
| 算法 / 研究项目 | 论文、方法、数据、实验和复现 | 问题定义、公式、基线、数据集和复现步骤 |

研究应回答目标用户是谁、项目解决什么问题、最短成功路径是什么、关键约束有哪些，以及 README 和专题文档应如何分工。源码、官方文档、配置样例和可执行测试是事实依据；高星项目只作为结构和表达参考。

## 2. 根据真实需求规划文档体系

| 文档 | 主要读者 | 主要任务 |
| --- | --- | --- |
| README | 首次访问者 | 判断项目价值，找到安装入口 |
| Quick Start | 新用户 | 完成一次最小成功操作 |
| Installation | 用户 / 运维 | 按平台或方式安装 |
| Usage / Guides | 日常用户 | 完成具体任务 |
| Configuration | 使用者 / 管理员 | 理解配置和安全边界 |
| Architecture / Design | 维护者 / 贡献者 | 理解模块、数据流和取舍 |
| API / CLI Reference | 集成开发者 | 查询参数、接口和返回值 |
| Troubleshooting | 用户 / 运维 | 根据现象定位问题 |
| Contributing | 贡献者 | 了解开发、测试和提交约定 |
| Security | 用户 / 维护者 | 报告漏洞并理解安全政策 |
| Changelog / Releases | 用户 / 维护者 | 查看版本和升级信息 |
| License / NOTICE | 所有读者 | 确认许可与第三方通知 |

只创建有实际内容的文档。小型项目不必创建空章节；大型项目应把安装、配置、API 和运维细节从 README 拆出。每个主题维护一个权威来源，通过链接引用，避免整段复制造成漂移。

## 3. 决定主文档语言与 i18n

主语言根据目标用户、项目生态和维护能力决定，不默认使用中文或英文。

| 主要受众 | 主语言建议 | 补充策略 |
| --- | --- | --- |
| 全球开发者 / 国际生态 | 英文 | 按需求提供完整中文文档 |
| 中国用户为主、面向国内场景 | 简体中文 | 提供英文简介、安装入口和关键术语 |
| 中英文均为核心受众 | 选定一种规范语言 | 另一语言版本同步更新并提供切换入口 |
| 内部 / 本地项目 | 团队实际工作语言 | 不为公开传播额外维护翻译 |

决策时检查 Issue/PR 语言、用户分布、生态默认语言、平台和依赖文档语言、搜索关键词、维护者翻译能力及未来受众。

- README 开头提供语言切换链接，例如 `[简体中文](README.zh-CN.md) | [English](README.md)`。
- 明确规范版本，其他语言版本同步更新。
- 保留产品名、命令、参数、路径、环境变量和 API 原始写法。
- 安装、安全、配置和兼容说明必须完整同步。
- 不确定的术语标记待确认，不编造本地化产品能力。
- 更新主语言文档时检查其他语言版本的链接与步骤。

避免维护内容重复且没有语言差异的 README 副本。

## 4. README 结构与发布会原则

README 第一屏应回答项目是什么、解决什么问题、读者下一步该做什么。推荐依次呈现项目定位、关键价值、真实预览或演示、最短安装路径、常见场景、重要边界、完整文档与许可证入口。

README 是项目入口，不是内部设计、历史过程和所有配置的汇总档案。长篇技术细节放入专题文档。

### 发布会原则

把公开 README 写成以用户价值为主线的产品介绍：先说明项目解决的问题、提供的能力和实际收益，再讲实现方式与使用路径。

- 以真实能力和用户场景组织叙述，不按开发时间线罗列工作过程。
- 用具体功能、输入输出、示例和可验证事实支撑价值表达。
- 优先展示已具备的优势、差异化能力和经过验证的设计选择。
- 性能、兼容性和覆盖范围数据附带条件、版本和测试环境。
- 不成熟能力、限制和未验证事项如实披露，放在合适的边界章节。
- 避免“遗憾的是”“仅仅”“仍明显落后”“效果有限”等自我贬低式措辞，改为说明支持范围、适用条件和实际行为。
- 较弱数据提供上下文和改进方向，不删减关键数字、不改变口径、不夸大结论。
- 不写无法由源码、测试、官方资料或实际产品验证的宣传承诺。

发布会原则调整叙述顺序与重点，不改变事实、不隐藏重要限制、不制造虚假比较。

## 5. 重要内容必须有事实依据

对照源码、目录、清单文件、默认配置、实际安装器、命令参数、测试、CI、上游官方资料和已记录的设计决策。

区分信息状态：

- **已验证：** 已实际执行，或由权威源码、官方文档直接确认。
- **有来源、未执行：** 操作来源明确，但当前环境尚未运行。
- **待确认：** 依赖版本、地区、账号灰度或资料不足，暂不能承诺。

不得编造功能、命令、路径、性能数据、市场上架状态、兼容版本或测试结果。平台界面变化时，说明版本与地区边界并链接官方资料。

## 6. 示例与可复现性

示例应短小、完整、可复制，并说明前置条件、输入、执行步骤和预期结果。配置示例使用真实键名和合法值；凭据使用占位符；示例数据明确标记；算法与研究项目记录数据集、预处理、参数、随机种子、硬件和指标；性能数字附测试方法、环境与版本。代码变更后同步更新示例和文档。

## 7. 许可证、来源与 i18n 发布

发布前按 [第三方内容与许可证审查规范](third-party-license-review.md) 检查文件级来源、许可、署名、NOTICE 和再分发条件。项目许可证应与文件来源一致，第三方文件保留各自版权和通知，README 指向真实许可证文件，图片、字体、数据集、模型和二进制资产具有明确来源及许可。

## 8. 公开文档发布门禁

- [ ] 已识别项目类型、目标用户和维护者。
- [ ] 已研究同类型代表项目的文档结构，并记录采纳或舍弃的设计。
- [ ] 已确定 README 主语言和 i18n 策略。
- [ ] README 第一屏说明项目价值与最短使用路径。
- [ ] 功能、命令、路径、配置、版本和数据均有真实依据。
- [ ] 安装步骤已验证，或明确标记未执行。
- [ ] 相对链接、外部链接、图片和代码引用有效。
- [ ] 示例与当前版本一致，可以复现。
- [ ] 许可证、版权、NOTICE 和第三方来源通过检查。
- [ ] GitHub 页面渲染正常，移动端表格和长代码处理合理。
- [ ] 完成对照源码的事实审查和独立文档审查。
- [ ] 没有把计划、假设或未验证能力写成现状。
