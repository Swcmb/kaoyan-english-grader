# 本机与私有项目文档规范

本规范适用于本机开发环境、私有仓库、团队内部系统、个人知识库和 Agent 工作区中的文档。公开开源项目文档遵循 [open-source-docs.md](open-source-docs.md)，GitHub Markdown 的通用结构与排版遵循 [github-content-writing.md](github-content-writing.md)。

## 目标与边界

本机文档的首要目标是帮助当前维护者安全、可重复地完成工作，包括环境准备、开发、调试、部署、恢复和迁移。

文档可以包含项目专属约束和内部操作流程，但必须控制访问范围。主机信息、私有地址、内部架构、用户数据、凭据和组织信息不得因为写入文档而自动成为可公开内容。

## 1. 文档分类与存放位置

根据文档的生命周期和读者划分目录。推荐结构：

```text
project/
├── AGENTS.md                  # Agent 执行约束和仓库入口
├── README.md                  # 项目用途和公共使用入口
├── docs/
│   ├── architecture/          # 稳定设计与决策
│   ├── development/           # 本地开发和调试
│   ├── operations/            # 部署、备份、恢复与运维
│   └── decisions/             # ADR 和重要取舍
└── .local/                    # 本机私有记录，不提交版本控制
    ├── environment.md
    ├── secrets.example.md
    └── experiments/
```

这是一个目录建议，不要求每个项目机械创建全部目录。小项目可以将少量稳定文档放在 `docs/` 根部。

| 文档类型 | 推荐位置 | 内容 |
| --- | --- | --- |
| Agent 规则 | `AGENTS.md`、工具专属入口 | 作用范围、执行约束、验证要求 |
| 开发说明 | `docs/development/` | 依赖、构建、测试、调试 |
| 运维手册 | `docs/operations/` | 部署、回滚、备份、恢复 |
| 设计决策 | `docs/decisions/` | 背景、选项、决策和后果 |
| 本机环境记录 | 私有目录或本地笔记库 | 主机路径、端口、设备和个人设置 |
| 实验记录 | 私有实验目录或研究目录 | 假设、参数、结果和复现方式 |

`.local/` 并不自动具有私有属性。若使用版本控制，应通过明确的 ignore 规则排除私有目录，并检查 Git 追踪状态。

## 2. 分离稳定事实、当前状态和计划

每份操作性文档应明确内容属于哪种状态：

- **稳定事实：** 已经验证且长期有效的项目约束、接口或架构。
- **当前状态：** 特定日期、机器、版本或配置下的实际情况。
- **计划：** 尚未执行的目标、方案或迁移步骤。
- **假设：** 需要实验或检查才能确认的判断。
- **历史记录：** 已被新状态替代的旧配置或故障过程。

记录当前状态时注明时间、版本、主机或环境。计划不能写成已完成，未复现的原因不能写成确定根因。

## 3. 环境与命令必须可复现

本地开发指南至少说明：

- 操作系统、运行时和关键工具版本。
- 安装依赖、启动服务、构建和测试的命令。
- 必需的环境变量及其用途。
- 数据目录、端口和服务依赖。
- 预期输出、健康检查和成功标准。
- 常见故障的诊断方式。

命令按目标 Shell 编写。Windows PowerShell、CMD、Bash 和 Zsh 的路径、引号、变量语法不同，不要将一种 Shell 的命令伪装成跨平台通用命令。

使用真实项目路径时说明它是示例路径还是当前机器的实际路径。迁移说明应记录源路径、目标路径、数据量、校验方法和回滚方式。

## 4. 安全处理机密和个人环境信息

不得提交以下信息：

- API Key、访问令牌、密码、私钥、Cookie 和会话文件。
- 未经授权的客户数据、个人数据或生产数据。
- 可直接访问私有服务的敏感地址、内部网络拓扑和管理入口。
- 可能绕过账号、访问控制或组织安全策略的信息。

文档只说明凭据名称和注入方式，使用 `YOUR_API_KEY` 等占位符。示例配置使用 `.env.example`，真实 `.env` 加入忽略规则。日志、截图和命令输出在分享前检查脱敏。

机器名、个人用户名、绝对路径、局域网地址和设备序列号也应按必要性处理。只有在本机操作确实依赖它们时才记录，并放入私有文档。

## 5. 记录变更、迁移和回滚

会改变数据、服务或开发环境的操作，应至少记录：

1. 变更目标和适用范围。
2. 执行前状态与备份位置。
3. 精确命令和操作顺序。
4. 预期结果及检查方式。
5. 失败时的停止条件。
6. 回滚步骤和数据恢复方法。

对于磁盘迁移、容器卷迁移、数据库升级、代理配置和系统级设置，不以“命令成功退出”作为验收。需要检查实际数据、挂载路径、服务状态和应用读写行为。

操作不可逆或会影响生产数据时，先备份并验证恢复路径。风险无法确认时暂停操作，明确列出不确定项。

## 6. 避免重复与过期文档

同一事实应有唯一权威来源。其他文档使用链接引用，不要复制多份互相漂移的完整配置说明。

更新配置、目录、端口、安装方式或脚本时，同步更新对应 runbook。为高频变化内容添加最近核验日期；过期内容标记为历史或归档，避免读者把旧记录当成当前操作步骤。

实验记录应保留假设、环境、参数、实际输出和结论。无法复现的记录标记限制，不将一次偶然结果上升为通用规则。

## 7. Agent 操作规范

为 Agent 提供的本地规则应明确：

- 允许修改的路径和禁止触碰的路径。
- 执行前需要查看的配置、日志和状态。
- 具有破坏性的命令及其审批要求。
- 每项任务的成功标准与验证命令。
- 失败时应保留的证据和回滚方式。

优先使用最小变更。只修改完成任务所必需的文件，不顺手重构无关模块。先检查当前状态，再执行操作；修改后运行对应测试并报告真实结果。

## 8. 本地文档发布或共享前的检查

本地文档需要分享、迁移到公共仓库或提交团队知识库时，逐项检查：

- [ ] 是否包含密钥、令牌、Cookie、个人信息或生产数据。
- [ ] 是否暴露个人绝对路径、机器名或内部网络信息。
- [ ] 是否将未验证假设写成事实。
- [ ] 命令是否包含不可逆操作或对生产环境的影响。
- [ ] 截图和日志是否完成脱敏。
- [ ] 文档是否有唯一维护位置，旧版本是否已标记。
- [ ] 内容是否适合目标读者和目标访问范围。
- [ ] 公开发布时是否满足 [公开开源项目文档规范](open-source-docs.md)。
