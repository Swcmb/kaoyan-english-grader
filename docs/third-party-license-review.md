# 第三方内容与许可证审查规范

本规范适用于复制、改编、翻译、重命名、vendor、再分发或发布第三方代码、Skill、Prompt、配置、模板及其他材料。

**许可证判定必须落到文件或明确的路径范围，不能用“整个项目”替代文件级证据。**

## 适用范围

| 操作 | 是否审查 |
| --- | --- |
| 从仓库或网站复制文件、代码片段、Skill、Prompt、配置或模板 | 是 |
| 将依赖源码 vendor 到仓库 | 是 |
| 翻译、改写或重命名第三方材料 | 是 |
| 发布包含上述材料的产物 | 是 |
| 从零独立实现同一功能 | 无需进行第三方许可判定；仍需为新文件确定许可标识 |

改写或翻译包含第三方材料的内容，仍然需要审查。

## 判定单位与证据

### 内容类别

| 类别 | 对象示例 | 审查重点 |
| --- | --- | --- |
| 源码 | `.c`、`.h`、`.py`、`.rs`、Makefile | 文件头、源码许可、版权声明 |
| 文字 | README、`docs/**`、注释、Issue 模板、幻灯片 | 文档许可、署名、改编和再发布条件 |
| 数据与配置 | TOML、YAML、Schema、样例数据 | 来源、许可范围、第三方内容 |
| 第三方产物 | vendor 依赖、字体、图片、二进制 | 各自许可证、NOTICE、再分发条件 |

### 证据检查顺序

1. 文件级 `SPDX-License-Identifier` 和版权声明。
2. 明确覆盖目标路径的 `LICENSE` / `COPYING`。
3. 文件内版权、来源标记和许可文本。
4. 上游 README、贡献指南或发布说明中的明确声明。

证据冲突时保留冲突信息并暂停判定。SPDX 标识表示许可证，不单独证明版权归属，也不替代署名义务。

判定对象使用明确路径或 glob，例如 `src/**/*.c`、`skills/vendor-skill/**`。不要将“整个项目”用作未经证明的判定单位。

## 禁止的推断

| 错误推断 | 正确处理 |
| --- | --- |
| 根目录许可证自动覆盖所有文件 | 核对许可证声明的路径范围和文件级标识 |
| README 声明证明每个文件都使用同一许可证 | 继续核对文件来源和独立声明 |
| 子目录许可证覆盖仓库其他目录 | 仅按其明确范围解释 |
| 文件有 SPDX 即代表署名完成 | 检查版权人、来源、LICENSE 和 NOTICE |
| 仓库公开即允许复制 | 未声明许可按“未声明”处理 |

## 每条结论必须记录的证据

至少记录：

1. **上游许可证定位：** URL 或仓库路径，并标明相关条款。
2. **原文件证据：** 上游文件路径、SPDX 标识、版权声明或可确认来源的证据。
3. **目标范围：** 明确的目标文件路径或 glob。

同时建议记录上游仓库、版本或提交 SHA、获取日期、修改方式、目标路径和须保留的通知文件。

缺少关键证据时标记为 **未声明 / 待确认**，暂停复制、改编和再分发。公开仓库、搜索结果和没有异议都不构成授权。

## 常见许可证兼容性边界

| 许可证 | 处理原则 |
| --- | --- |
| MIT / BSD-2-Clause / BSD-3-Clause / ISC | 通常可与 GPL 系列组合；保留原始版权和许可通知，其他 BSD 变体另行核验 |
| Apache-2.0 | 与 GPL-3.0 兼容；与 GPL-2.0-only 不兼容；保留 Apache 许可证和适用 NOTICE |
| GPL-2.0-only | 不要与 GPL-3.0-only 代码合并为受单一 GPL 版本约束的作品 |
| GPL-2.0-or-later | 若权利人允许后续版本，可选择 GPL-3.0；仍需核对原始声明 |
| 专有或未声明 | 未获明确授权前停止复制和再分发 |

GNU 将 Apache-2.0 列为与 GPL-3.0 兼容；Apache 软件基金会也说明 Apache-2.0 软件可纳入 GPL-3.0 项目。Apache-2.0 与 GPL-2.0 的不兼容，不能泛化为与 GPL-3.0 不兼容。

不要编造 `Apache-2.0-exception` 等 SPDX 例外标识。`WITH` 只能引用 SPDX 例外清单中的真实标识。Apache 2.0 的 SPDX 标识是 `Apache-2.0`。复杂链接关系、衍生作品边界、专利条件和多许可证组合应单独审查。

权威资料：

- [GNU：许可证兼容性与重新许可](https://www.gnu.org/licenses/license-compatibility.en.html)
- [Apache Software Foundation：Apache 2.0 与 GPL 兼容性](https://apache.org/licenses/GPL-compatibility.html)
- [GNU GPL FAQ：GPLv2 与 GPLv3 兼容性](https://www.gnu.org/licenses/gpl-faq.en.html#v2v3Compatibility)
- [SPDX：许可证例外清单](https://spdx.org/licenses/exceptions-index.html)

## 本仓库许可政策

### 新建项目默认值

新项目默认采用 `GPL-3.0-or-later`。一次性脚本、个人配置和教程仓库可根据实际分发目的另行选择。该默认值不会自动改变已有仓库许可证；修改已有项目许可必须取得维护者明确授权。

### 当前仓库

本仓库原创内容采用 `GPL-3.0-or-later`。根目录 `LICENSE` 和 `COPYING` 保存完整 GPLv3 文本。新建原创 Markdown 文件应添加 `SPDX-License-Identifier: GPL-3.0-or-later` 文件级标识。

第三方文件保留上游 SPDX 标识、版权声明和许可证。仓库默认许可证不会覆盖独立授权的第三方文件。

### 文件头和通知

新建原创文本文件时，按文件格式选择合法注释位置：

- Markdown / 普通文本：首行或首个有效注释位置。
- Shell：保留 shebang，并在其后添加标识。
- Python：遵循编码声明位置要求。
- 其他源码：遵循对应语言的文件头规范。

第三方材料保留上游版权、许可证、NOTICE 和来源信息。不得为生成产物、lockfile 或第三方文件伪造所有权声明。

### 署名完整性

引入第三方材料时，检查许可证全文、适用 NOTICE、文件级版权/SPDX/来源信息，以及改编文件到原始版本的追溯关系。

仓库引入第三方材料后，应增加自动化署名完整性检查，断言许可证文本、NOTICE 来源和文件级标识未丢失。新增、移动或重命名第三方文件时，同步更新检查清单和 NOTICE。

### 许可变更

更换项目许可证、删除上游通知或扩大现有许可证范围，必须取得维护者对该次变更的明确授权。证据冲突或授权边界不清时暂停操作，并报告路径、证据和未解决问题。
