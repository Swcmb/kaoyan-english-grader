# 复制之前先检查许可证

在把第三方内容引入项目，或发布任何包含第三方材料的产物之前，先确认你有权这样做，以及需要履行哪些条件。

宽松许可证通常要求保留版权声明和许可证文本。这个要求很简单，却容易在重命名、重构、移动文件或重新打包时丢失。

🔴 **署名不是礼貌性致谢，而是许可证授予复制和再分发权利时附带的条件。** 例如，分发 MIT 许可作品时，必须保留其版权声明和许可声明。遗漏这些通知可能导致分发行为不符合许可证条件。

## 何时使用

- 从其他项目复制文件、Skill、Prompt、配置或代码片段。
- 将依赖源码 vendor 到仓库，而不是通过包管理器安装。
- 发布包含上述任一第三方材料的产物。
- 重命名、移动或重新打包已经包含第三方内容的项目。
- Agent 生成的代码与某个已知库或项目中的实现高度相似，需要核查来源。

## 执行流程

### 1. 复制之前先找到许可证

在复制之前检查目标文件本身及其上游仓库：

1. 查看文件头的 `SPDX-License-Identifier` 和版权声明。
2. 查找覆盖该文件路径的 `LICENSE`、`COPYING` 或 `LICENSES/` 文件。
3. 阅读 README、NOTICE 和贡献指南中的明确授权说明。
4. 核对许可证适用的文件路径范围、版本和上游提交。

如果没有许可证文件、SPDX 标识或其他明确授权声明，将其标记为 **未声明**。公开仓库不等于开放许可证。暂停复制、改编和再分发，向权利人确认；也可以从零独立实现功能，但不能把来源不明的原始内容带入项目。

### 2. 阅读许可证的实际义务

不要只看许可证名称。打开许可证全文，核对具体条款、分发形式、修改行为和文件范围。

| 许可证 | 再分发时需要重点核对的事项 |
| --- | --- |
| MIT / BSD / ISC | 保留适用的版权声明和完整许可证文本 |
| Apache-2.0 | 保留版权、许可证和适用的 NOTICE；修改过的文件需标明变更 |
| MPL-2.0 | 履行覆盖文件的许可证、源代码提供和修改通知义务；不能简单推断整个项目都必须采用 MPL |
| LGPL | 按具体版本履行库修改、源代码、重新链接或安装信息等适用义务 |
| GPL / AGPL | 按版本、衍生作品边界和分发方式履行 copyleft、源代码及其他义务；AGPL 还涉及网络交互场景 |
| CC BY / CC BY-SA | 保留署名、许可链接和修改说明；BY-SA 还要求符合相同方式共享条件 |
| 未声明 | 未取得明确许可前，不复制、改编或再分发 |

这张表是审查入口，不代替许可证全文。尤其不要把 MPL、LGPL、GPL 和 AGPL 的义务简化为同一条规则。

### 3. 将署名信息放在三个位置

本仓库采用以下三处留痕约定，降低重命名、移动、重构和重新打包导致信息丢失的风险：

1. **许可证全文**：将上游许可证原文按字节完整保存在 `LICENSES/` 目录。不要用摘要或自行改写的文本代替。
2. **仓库级 NOTICE**：在 `NOTICE` 的第三方材料章节中，记录来源仓库、原始路径、权利人、许可证、取得版本或提交，以及改编内容。
3. **文件级标识**：在每个引入或改编的文件中保留版权人、来源、许可证标识和修改说明。文件移动或重命名后，这些信息仍应跟随文件。

这三处是本仓库的工程留痕标准。各许可证本身要求的法律通知、保留条件和分发义务仍以许可证原文为准。

文件级标识示例：

```text
Copyright 2026 <copyright holder>
Adapted from <upstream repository and file path>.
Changes: <translation, rename, adaptation or trimming summary>.
SPDX-License-Identifier: <upstream SPDX identifier>
```

不要擅自把第三方文件的 SPDX 标识改成仓库根许可证。仓库自有内容与第三方文件可以有不同的文件级许可证。

### 4. 编写会因署名丢失而失败的测试

新增第三方材料时，同时新增自动化测试，至少验证：

- 完整的上游许可证文本仍然存在，且没有被摘要或改写。
- `NOTICE` 仍然记录来源、权利人和许可证。
- 每个引入或改编的文件仍带有文件级来源和版权信息。
- 文件路径发生移动或重命名时，测试清单也必须显式更新。

测试应实际读取文件并断言内容，不能只检查目录或文件名。推荐使用项目已有测试框架；若仓库没有测试框架，可使用 Python 标准库 `unittest`。

本 Skill 所在仓库的测试命令：

```bash
python -m unittest discover -s tests -v
```

### 5. 明确说明改动

在 `NOTICE` 和对应文件中说明具体做了什么，例如：

> 改编自上游项目的 `check-the-licence-before-you-copy`，翻译为中文并适配本仓库的文件级许可证审查和署名测试流程。

改编、翻译、重命名、移动或删减都应如实记录。不要将第三方方法或内容描述为完全原创。

### 6. 无法确认时，先不要引入

涉及个人工作流、第三方产品、个人身份或特定组织内部流程的材料，不应未经确认就泛化后放进自己的项目。无法确定许可边界、权利人或署名义务时，保留证据并暂停操作，等待授权确认。

## 常见反模式

- **只在提交信息中署名**：提交记录可能被压缩、合并或脱离源码分发，不能替代文件和 NOTICE 中的必要信息。
- **认为改写得足够多就不再是改编**：从某个文件出发进行翻译、改写或重构，仍应审查其来源和授权。
- **用许可证摘要替代原文**：摘要不能替代许可证要求保留的完整文本。
- **发布时才补 NOTICE**：到发布阶段，文件可能已经改名和移动，来源更难准确还原。
- **只保留一处署名**：文件、NOTICE 和许可证文本应各自满足对应的留痕要求。
- **把仓库根许可证覆盖到所有文件**：第三方文件保留自己的许可证标识和适用条件。

## 事件案例

上游项目记录过一次包含 44 个 Skill 的发布，其中 23 个 Skill 改编自一个 MIT 许可项目。维护者在许可证文本、NOTICE 和每个改编文件中保留署名，并添加测试，确保任何改编文件丢失版权行时测试都会失败。

在添加署名到正式发布之间，项目名称被修改两次，每个 Skill 都被重命名，文件也通过 `git mv` 移动。测试的目的正是防止这些维护操作静默删除来源信息。

上游项目还明确表示：如果原作者不希望材料继续分发，会及时移除相关内容。尊重权利人的移除请求，并保留清晰的沟通记录。
